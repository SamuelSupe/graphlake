# GraphLake 生产性能与可靠性优化方案

设计日期为 2026-11-16，代码基线为 `8189ac391ea3ef81e79a7864ba845e53a1bb7a2a`。实施与实测见 [S0 和 S1 验证记录](production-optimization-s0-s1.zh-CN.md)、[S2 和 S3 验证记录](production-optimization-s2-s3.zh-CN.md)、[S4 和 S5 验证记录](production-optimization-s4-s5.zh-CN.md)、[S6 备份恢复验证记录](production-optimization-s6.zh-CN.md)及 [S6 托管本地表验证记录](production-optimization-s6-managed.zh-CN.md)，实现位于 `codex/production-optimization-plan`。

目标是同时降低小结果查询与小批同步的实际成本，并让数据新鲜度、算法规模和恢复能力成为可验证的产品契约。在核心门禁、主要连接器下推、本地同步、数据可信度与恢复闭环验收前，暂停新增连接器。

优先顺序：先建立回归和成本基线，再减少来源读取，随后解决 UUID 与复合键增量写入，补齐删除对账和 CSR 新鲜度，最后完成算法容量与集群存储恢复。能力说明及资源预检可以提前落地；不要用提高默认预算掩盖成本问题。

## 1 当前实现与问题边界

本节描述 `8189ac3` 的设计基线。实施进度和对应的实测结果见上方验证记录。

| 问题 | 当前实现 | 设计结论 |
| --- | --- | --- |
| 返回一行仍完整读取 | `read_filters::query_filter` 保留业务键条件；通用 `sql_term` 只处理可表示的整数比较及 NULL。SQLite、MySQL 和 ClickHouse 在返回 TableProvider 前完成快照物化 | 普通属性、类型、LIMIT 与校验必须一起处理；协议本身分批读取不等于查询执行流式化 |

| 算法规模 | 社区检测额外预留约 `512V + 256E`，另有图与结果内存；分布式 CSR 支持路径遍历、PageRank/WCC 等特定操作 | 增加算法能力矩阵和执行前预检；社区检测与 Node2Vec 不能承诺增加 Worker 即分摊状态 |
| 集群本地表与恢复 | 共享绝对路径、目录独占锁；备份恢复链不包含本地表定义与历史 | 先补完整恢复，再增加复用现有对象存储的集群模式；保留单机和共享目录兼容路径 |

## 2 不可破坏的契约

1. SQL、Cypher、Gremlin 的值、NULL、类型、重复行、业务键和权限隔离语义保持一致。有确定性排序时逐行同序；无 ORDER BY 的 LIMIT 不承诺某一固定行，但行数及过滤必须正确。
2. 下推不能跨过尚未执行的权限过滤、去重、冲突校验、SCD2、Join 或其他改变结果基数的操作。残余过滤不能被 LIMIT 截断。
3. 不改变用户源表，不自动建索引、触发器或开启数据库日志。源端索引不足时展示诊断和建议。
4. 数据、水位、删除及代次必须作为一个快照提交。提交前失败保留旧快照；提交后不能因历史写入失败把已提交数据当成未提交。
5. 查询固定来源与本地表代次。刷新、重试、GC、备份不能使查询混读两代数据。
6. 保留现有单机部署、接口入口、凭据环境变量、权限及模型发布流程。新格式明确版本，先升级读者，再启用新写者。

## 3 来源下推与按需读取

### 3.1 能力必须按操作与类型判定

复用 DataFusion 的 TableProvider、`Exact / Inexact / Unsupported` 和现有 `sql_read::Pushdown`；增加必要的类型化内部请求与诊断结果，不创建第二套通用查询优化器，也不重写所有连接器为一套框架。

内部扫描描述包含投影列、类型化谓词、排序、可下推的行数限制和已有聚合描述。类型值保留整数宽度、无符号范围、Decimal 精度、日期及时间戳单位与时区；公开的 JSON `Predicate` 暂时保持兼容，在有 schema 后转换。每个连接器返回已接受的条件、残余条件、精确性和拒绝原因。

能力展示分为“连接器可表达”和“本查询实际采用”。即使连接器支持 LIMIT，当前映射可能因为重复键校验或残余条件无法使用。MySQL 协议兼容数据库分别声明能力，不因共用驱动而继承 MySQL 的一致性与类型结论。

| --- | --- | --- | --- |

### 3.2 下推的语义条件

- 先支持直接映射的单表标签，处理 `= / != / < / <= / > / >= / IS NULL / IS NOT NULL` 与 AND；再扩展 IN/OR。OR 必须整个子表达式可证明安全，不能只取一个分支。值使用参数绑定；不支持绑定的协议仅使用有类型约束的专用编码，标识符单独引用。
- 精确下推要求数据库比较结果与 GraphLake 相同。安全的超集过滤可标为 Inexact 并在本地复核，不能漏行；无法证明超集时完全留在本地。类型转换、浮点特殊值和隐式字符串转换不得靠试探猜测。
- 字符串处理明确大小写、尾随空格、Unicode、NUL 与排序规则。SQLite 的 BINARY/NOCASE/RTRIM 语义不同，动态存储类型也会影响比较；不能只看声明类型就标为 Exact。[SQLite 类型与排序规则](https://www.sqlite.org/datatype3.html)
- LIMIT 只越过已精确完成的过滤和可证明不改变行数的投影。保留外层 LIMIT；有 Inexact 或本地残余谓词时不下推提前截断。[DataFusion TableProvider 契约](https://docs.rs/datafusion/latest/datafusion/datasource/trait.TableProvider.html)
- Top-N 首批只支持简单列及确定性完整排序，验证 NULL 顺序、升降序和比较规则。非唯一排序的并列行不得作为逐行等价基准；不擅自为用户改变排序。OFFSET 后续在同等条件下读取 offset+limit，不用不稳定分页假装降低成本。
- 聚合首批扩展现有 COUNT/MIN/MAX，包括空集和 NULL 契约。GROUP BY、SUM、AVG 作为下一层能力，先证明分组等价、累加类型、溢出及合并规则；不以浮点 SUM 顺序变化冒充完全等价。
- SQL、Cypher、Gremlin 都以转换后的实际逻辑计划验证。先支持三种语言能证明的简单单标签过滤/限制；复杂多跳、相关 CALL、UNION、自连接、多映射和 SCD2 保留原路径并显示原因。

### 3.3 业务键与校验是快速路径的前置条件

当前键过滤保留同一个键的全部候选行，允许现有校验发现冲突；属性过滤可能只留下其中一行，LIMIT 更可能跳过重复。因此不能直接移除 `filters.retain`。

按以下顺序建立证明：源端有效且覆盖所需键语义的唯一约束；GraphLake 管理且已完整校验的不可变快照；同一个固定来源快照中的完整校验。证明必须绑定表身份、schema、映射、键语义和快照代次。可变源表不能沿用上次发布或上次查询的证明。

SQLite 的声明主键、部分/表达式索引、NULL、排序规则及存储类型需要分别检查；MySQL 检查实际索引与引擎，不接受任意“可信键”开关。缺少证明时保留现有检查，可以把重复检测本身放在来源执行以减少传输，但其源端扫描成本必须计入。

现有错误语义也属于契约：NULL 键如何处理、动态类型非法值是否必须报错、重复映射如何合并，都要先锁定行为。SQLite 非 STRICT 表无法仅凭 schema 证明全表类型合法时，使用同快照校验或原路径；不默默把原本报错的查询变为成功。

因此验收区分两个事实：具有可靠键与类型约束的表可以做到读取一行；无约束的表若要求全局冲突检查，仍可能扫描全表。诊断明确显示验证读取，不宣传所有 `LIMIT 1` 都具有常数成本。

### 3.4 从完整物化过渡到按需读取

第一步先在现有物化路径前执行被证明安全的远端 WHERE/LIMIT，直接解决一行结果的多余传输。第二步将 SQLite、MySQL、ClickHouse 分别改为惰性 TableProvider：规划只取元数据，执行阶段按需产出 RecordBatch，驱动页/批次和缓冲队列都受内存预算约束。

SQLite 阻塞读者使用现有阻塞任务和有界队列；MySQL 管理事务连接所有权及串行查询；ClickHouse 复用 IPC 解码器并在消费者取消时结束请求。提前停止后的连接必须确认可重用，否则丢弃，不能把未读响应交给下一条查询。

同表多次消费、重扫、自连接及业务键校验与查询共用数据时，保留有预算的快照缓冲/溢写，或在同一可靠快照重扫。先只对单消费者直接扫描启用惰性读取，避免一个连接上多个未完成流相互等待。事务、版本校验及资源预留持续到最后一个消费者结束；取消、超时、客户端丢弃结果都需要释放游标、连接与临时文件。

### 3.5 成本观测

保留现有 ReadMetrics，追加每个来源的诊断，区分：数据库实际 examined/scanned 行数、连接器接收行数、验证行数、Arrow 内存字节、可测的网络字节、文件读取字节、溢写字节、首批可用时间及总耗时。服务端扫描数拿不到时返回 unknown，不用接收行数代替。原 `loaded_rows` 含义保持不变。

EXPLAIN 显示计划中的下推、残余条件、验证方式及回退原因，不为了展示预估执行全量读取。真实执行返回实际采用路径与计数；数据库计划或系统指标作为基准报告的补充，元数据请求与数据扫描分开计数。

## 4 增量同步的读写成本

### 4.1 类型化水位与稳定分页

复用第 3 节的类型化扫描请求，传递 `watermark >= L`，其中 `L = 已提交水位 - 配置的重读窗口`，默认窗口为零，保持现有含边界重读语义。日期、时间戳及全部现有整数宽度不经过 JSON 浮点或字符串猜测；无损转换失败则回退并报告原因。

MySQL 连接仍固定 UTC，但区分 TIMESTAMP 的时区换算与 DATETIME 的无时区墙上时间；比较参数与当前解码类型保持一致，并覆盖微秒精度。PostgreSQL 分别处理 date、timestamp、timestamptz；特殊值沿用现有支持或拒绝规则。[MySQL 日期与时间语义](https://dev.mysql.com/doc/refman/8.4/en/datetime.html)

单次运行固定读快照，以该快照的最大水位作为上界 U；无变化时保持旧水位。需要分页时使用 `(watermark, 完整主键)` 游标和一致排序，在同一快照内读取 `[L,U]`，不使用 OFFSET。分页游标只负责同一运行内翻页，下一轮仍重读下边界，不能持久化复合游标后遗漏相同水位的后提交行。先使用单条流式 SELECT 完成支持的数据库路径，只有协议需要分页时才引入游标分页。

水位、schema、键定义、行数和提交时间写入同一新代清单；不再依赖“最后一个 delta 的 MAX 一定等于全表水位”，因为重读窗口、删除或未来重排都会破坏这一假设。高水位在增量运行中不倒退；全量对账可以在新代中重新建立水位。没有数据的全量快照也必须有合法清单表示。

没有实际变更时保留原数据代次与文件，只更新成功观察记录；同步新鲜度使用这次观察，CSR 是否追平使用数据代次。不能因业务水位长期不变就误报停更，也不能把一次无变化的水位查询当成完成了删除对账。

源表缺少适用水位索引时，即使只传回少量行也可能全扫描。显示来源执行计划/索引诊断；优先评估 `(updated_at, tenant_id, user_id)` 等索引，但不自动修改用户数据库。索引顺序按实际范围与排序验证，不能保证一个复合索引适配所有查询。

### 4.2 UUID 与复合键的定位方案

保留现有 Parquet 基础文件、delta、覆盖位置与原子清单。为通用主键增加可重建的键位置索引，复用已经依赖的 SQLite B-tree，不引入 RocksDB、自研 LSM 或另一套查询数据存储。

索引只由同步写者使用，位于写者本机缓存目录；查询数据的唯一事实来源仍是 manifest 与 Parquet。HA 下不把 SQLite 索引放到网络共享目录。索引记录 `完整类型化键 -> 文件 ID、物理行位置`，元信息记录数据代次、schema/键指纹与编码版本。复用现有 Arrow RowConverter 的类型化编码思路；持久化编码必须加版本，依赖升级改变编码时重建，不能把实现内部字节当成永远稳定的外部格式。

首批优化 UTF-8 字符串/UUID、整数及其复合键。按配置字段顺序编码，保留类型与边界；禁止用分隔符拼接或仅存哈希，避免 `('a|b','c')` 与 `('a','b|c')`、字符串 `1` 与整数 `1` 混淆。空键继续拒绝，其他键类型保持语义正确的原路径并显示成本。

一次小批 upsert 查询键位置，读取命中行所需的行组来比较重读边界是否真的变化，标记旧位置并追加新行。查询不做每行索引查找，仍使用现有 Parquet 扫描和覆盖掩码；单列整数范围裁剪继续保留。有效索引下预期定位成本是 `O(Δ log N)`，实际旧数据读取以被命中行组为单位，不宣称严格逐行 I/O。

索引损坏、缺失或代次不一致时，禁止使用旧位置：可从已提交快照只读取键列重建，或显式退回全合并。重建是可见的 O(N) 维护操作，要受预算、取消及磁盘容量约束，不能隐藏在正常“小批增量”统计中。

### 4.3 原子提交与索引恢复

引入版本化新清单，兼容读取现有单文件与 GLPQ1。所有新代数据文件不可变；清单显式包含 generation、完整 schema、主键定义、水位、提交时间、来源快照信息、有效行数与文件引用。先实现读兼容，再启用新写入；旧程序不得读取不认识的新格式。

单表单写者执行：

1. 固定旧代 G，核对键索引代次 G，并生成本次候选数据、覆盖位置和新清单 G+1。
2. 将新文件写完、校验并持久化；在本机 SQLite 事务中更新键位置并写入 G+1，提交索引。此时索引只是未发布快照的派生缓存。
3. 在仍拥有写权限且旧代仍为 G 的条件下，原子发布 G+1 清单/指针。这是唯一数据提交点。
4. 更新任务结果与调度记录，最后按保留规则回收未引用数据。任务记录包含 committed_generation，提交结果可在重启后复核。

若步骤 2 后、步骤 3 前中断，已发布代仍是 G，索引 G+1 被判为不匹配并重建；步骤 3 后中断则按 G+1 恢复，历史缺失不回滚数据。索引提交失败时不发布；文件或清单不完整时不发布。完整刷新和 compaction 也遵守同一协议。索引不承担跨文件事务的事实来源责任。

S3 即实现本机查询对旧代的引用保护，或在保护机制到位前暂停旧文件删除；不能等到集群阶段才处理同步后立即清理与正在运行查询的竞争。

### 4.4 整理与长期成本

沿用小批追加和分区整理逻辑，逐步支持通用键。整理后更新被移动行的索引位置。不能把随机 UUID 的全表键列扫描、索引重建或基础文件全写排除在性能统计外。

阈值以 delta 字节、覆盖密度、文件数和查询读取放大为依据；现有 16/15 文件及 65,536 覆盖位置限制在新格式中显式版本化。先保留安全上限并测量，再调整；到阈值时安排受限整理，无法完成则背压/延后同步，不静默突破磁盘或内存预算。

最坏情况的大批更新、迁移、索引重建及全量对账仍可能 O(N)。目标是正常小批更新不每次全写，并证明覆盖至少 100 轮、跨过多个整理阈值后的累计写放大与查询成本；不能只展示第一次 delta 的收益。

## 5 删除可见性与数据可信度

### 5.1 删除与迟到分三种契约

| 同步方式 | 能捕获什么 | 无法保证什么 |
| --- | --- | --- |
| 水位加重读窗口 | 插入、更新、窗口内迟到/乱序提交 | 任意长事务、窗口外迟到、未推进水位的更新和物理删除 |
| 软删除标记或已有变更表 | 水位推进的删除事件；变更表中明确的删除键 | 没有产生事件的物理删除、在读取前清除的 tombstone |
| 定期全量对账 | 对账快照中的删除、遗漏与旧值 | 两次成功对账之间的立即删除可见性 |

增加可选软删除列/删除值定义，先把删除行读入并按完整键删除，再推进水位；不能在源端先过滤掉删除行。删除高水位记录仍保留已提交高水位，支持最终零行快照。源端 tombstone 保留期必须长于最大停机加重试时间；不满足时要求对账。

首版实现软删除列。接入已有变更表时，另行要求稳定事件 ID、可排序提交位置与操作类型，在事务顺序内折叠同一键的多次事件并持久化消费位置；它不能直接套用“每批完整主键唯一”的普通源表加载规则。在该契约实现前，变更表只作为后续接入选项，不计入已支持能力。

全量对账首版复用完整加载与原子替换，定时策略与增量分开记录，但共享单表写锁；失败保留旧代，不把失败尝试时间写成“最近成功对账”。调度持久化最近成功时间和下一次到期时间，增量繁忙不能永久饿死对账。之后才评估按分区比较键/摘要的对账，仍需能发现低水位内容更新。

数据库日志 CDC 是后续独立阶段：只有业务要求物理删除的严格低延迟，且周期对账无法满足时才启动。范围必须包含一致初始快照、日志位置、事务边界、幂等删除、schema 变化、日志过期和故障恢复；本轮不把窗口同步改名为 CDC，也不要求部署 Kafka。

### 5.2 新鲜度的事实与策略

每张本地表持久化最后成功提交、来源观察区间、最后成功全量对账、捕获方式、水位类型/值、当前代次和失败状态。业务时间水位不能直接当作来源提交时间；没有变更的旧业务数据不自动代表同步落后，最近同步成功也不代表所有物理删除已捕获。

每个模型增加可选的新鲜度策略：最大来源观察年龄、最大对账年龄、是否要求 CSR 与当前所依赖的本地代次一致、是否要求严格跨源快照。普通探索默认允许查看并显示状态；安全敏感调用显式启用严格策略，缺失事实、超限或不一致时在返回结果前拒绝。旧快照查询仍可作为历史查询执行，结果明确标注代次，不能冒充当前授权状态。

“确定性证据”不压缩成一个绿色布尔值。结果及 MCP 输出分别提供快照范围、删除覆盖方式、对账时间、CSR 代次和未满足条件，机器可读字段与 UI 一致。权限范围随原请求传递到下推和缓存，任何可信度诊断也不能泄露其他模型/租户信息。

删除可见时间按实际捕获方式给出：健康运行的轮询/软删除约为“等待下一轮 + 同步 + CSR 刷新”；物理删除靠对账时再加对账等待与耗时。停机、重试或源端不可用会延长它们。展示配置目标、实测延迟和当前是否超限，不把调度间隔当成硬保证。

### 5.3 CSR 与跨源版本

CSR manifest 增加构建完成时间及所依赖的本地表 generation 向量。同步提交后仅将相关模型标为待刷新，可配置自动刷新；合并连续事件，只保留最新目标，单模型单构建，失败重试有退避且可观测，限制构建并发及资源占用。

构建固定输入代次。构建完成时若来源已前进，可以保留已完成的历史代次，但必须继续标记落后并调度新目标；不能覆盖“最新已追平”状态。查询始终固定所选 CSR 代次，旧代不会被刷新中途替换。

跨来源用版本向量表达可重复性。保留 `require_consistent_snapshot` 的拒绝语义；来源观察时间差是诊断，不是共同事务证明。未来可把一组本地代次作为原子发布的命名快照组，使重复分析稳定，但不声称它们对应业务世界的同一个瞬间。

## 6 算法容量与分布式收益

### 6.1 清楚展示执行位置和资源

集中定义算法元数据，供命令行、API、模型健康页和文档复用：支持的路径、是否投影整图、是否支持分区执行、内存模型、可取消性及主要规模参数。PageRank/WCC 的分布式 CSR 路径与 Louvain/Leiden/Node2Vec 的本机投影路径分开展示。

社区检测对 10 万顶点、100 万条内部 links 的额外预留约为 307,200,000 字节，即约 293 MiB，已经超过默认 256 MiB，还没加投影图和结果。内部 links 数可能受方向、平行边处理影响，不能直接把源表行数当作它。预检返回实际/估计 V、E、额外工作区、总预算以及估计是否可靠。

如果现有 CSR 或可信统计可提供规模，在读取整图前预检；只有估计时，执行中仍逐批计费并可取消，不为了估计先扫描整图两次。Node2Vec 计入至少两份 `V × dimensions × Float32` 矩阵及采样/游走缓冲，不能沿用社区检测公式。

集群配置当前还把 `memory_mib` 限定为 16–256，仅建议“调大预算”对该入口不可用。增加受管理员与进程总预算约束的上限配置，保持默认值；并发接单、远端分区和 CSR 构建共享明确的节点资源上限，防止每项单独合法而合计耗尽内存。

### 6.2 社区算法优化顺序

先测投影、邻接、leiden-rs 构造与迭代各阶段的 RSS、实际分配和预留峰值，定位重复保存的端点/权重/映射。随后减少可证明多余的复制，及时释放阶段性状态，并评估直接消费紧凑邻接结构的有限接口改动。

内存估算与实测校准，但不单纯降低 `512V + 256E` 常数以让请求通过。保留种子、权重、孤立点、平行边、零权、取消与结果语义。目标是以测得的明确预算完成百万边夹具，减少实测峰值；不预先承诺必定装入 256 MiB。

分布式 Leiden/Node2Vec 需要独立算法与质量设计，不能借当前 Worker 调度假装完成。本次交付包括正确的规模准入、单机内存优化和能力说明；任意规模横向扩展明确不在这次实现范围内。

### 6.3 扩容评估与调度

先拆解当前跨源 Join 的来源读取、规划、分区、上传、下载、远端计算和最终合并耗时。小数据优先本机；只有可拆分工作量足够大且预估收益覆盖传输与调度时才自动分布式，保留显式策略用于复现。阈值来源于实测，不能把某一次 2.07/11.08 秒比值硬编码成规则。

基准覆盖 1/2/3 Worker，分别测固定总 CPU/内存的效率及每 Worker 资源固定的扩容收益；记录来源服务与对象存储是否为瓶颈。测低/高选择率、宽窄行、Join 倾斜、聚合与 PageRank/WCC，以及单请求延迟和并发吞吐。输出 P50/P95、总 CPU 秒、RSS、网络、对象请求与字节、重试和单位查询资源成本。

OrbStack 用于可重复的功能、故障与成本拆解；独立主机验证由实际独立主机提供。同一 Mac 上的多个虚拟机不能作为独立硬件扩容结论。外部机器未就绪时该验收项保持未完成，不阻塞其他工作，也不发布“增加机器即可加速”的结论。[现有历史验证范围](../deploy/cluster.md)

## 7 本地表高可用与恢复

### 7.1 先补完整备份

扩展现有备份/恢复清单，包含本地表定义、来源配置引用、刷新策略、历史、已提交 manifest、全部被引用的数据文件及 schema/水位信息。凭据仍引用环境变量，不导出秘密值。派生键索引可重建，缺失不影响快照可读；恢复后的重建成本需要展示。

备份固定各表代次并保护所引用文件，禁止边遍历活动目录边复制。单机首版可短暂停止同步提交、捕获清单后恢复同步；复制期间继续保护引用，完成后发布带摘要的备份清单。模型归档与本地表引用必须一并校验，避免恢复后模型指向不存在的表。

恢复先在新目录/命名空间校验文件、摘要、结构、定义和引用，再原子激活。支持逻辑表 ID 到新根目录的映射，不直接修改归档模型内容的版本哈希；旧绝对路径模型通过显式迁移生成新的模型修订，或要求恢复原路径。恢复中的调度默认暂停，完成数据查询和权限验收后再启用，避免刚恢复的副本立即被源端刷新覆盖。

沿用现有路径穿越、符号链接、文件类型与禁止覆盖不同内容的检查。损坏/缺失文件、部分上传及版本不兼容都必须使激活失败。恢复验收不仅检查服务启动，还要在源系统不可达的情况下读到副本，随后恢复来源并完成增量、删除与 CSR 刷新。

### 7.2 集群增加托管对象存储模式

推荐集群模式复用已有 S3 兼容存储和 etcd，把所有 Worker 必须挂载相同本地目录的要求移除；单机仍使用文件目录，共享目录作为兼容选项。首版不自建 Worker 数据复制或共识系统。

增加以稳定 table_id 引用托管副本的来源描述。已有 `local_<name>.data` 的界面映射体验保留；新模型修订使用逻辑引用，历史绝对路径来源仍走兼容读取。查询规划固定 table_id 对应的 generation，再将确切 manifest 与文件摘要引用传给 Worker，Worker 不自行读取 latest。

提交过程先写入不可变数据对象和 manifest，校验上传完成，再用 etcd 事务比较旧 generation 与当前领导权 fencing 标识，发布新指针；失败对象留待 GC。大 manifest 不存 etcd。任务状态、定义与指针纳入现有 HA 控制状态；旧 Coordinator 即使恢复网络也无法提交。失去租约时停止新任务，正在执行的任务不能越过最终 fencing 检查。

新 HA 协议即使把数据文件保存在共享目录，也由同一个 etcd 事务发布不可变 manifest 的指针；文件锁只作辅助互斥。不能先检查领导权、再单独替换可变路径并声称已经防住旧主提交。旧绝对路径模式保持其已记录的部署边界，迁移到逻辑引用后才启用新提交保证。

Worker 可使用有容量上限的本机缓存，缓存键包含对象身份、generation 和摘要；缓存淘汰不影响正确性。对象存储的冗余与可用性由部署层提供，文档明确故障域、容量、RPO/RTO；不称为 GraphLake 已实现多副本数据库。

### 7.3 快照保留与垃圾回收

当前目录锁只覆盖写者，不能证明旧文件无人读取。先引入查询与备份对代次的引用保护，再允许在线回收：本机使用活动引用；集群复用任务/租约状态并考虑最大查询期限及重试窗口。控制状态不可用时停止回收，保护中及保留期内的文件均不可删除。

固定代次与登记引用必须在同一受控步骤完成，GC 标记后禁止新增该代次的引用，避免“已选中旧代但尚未登记”与删除交错。无法续租的查询在其保护窗口结束前停止使用数据；重试必须重新确认原代仍被保护，不能悄悄改读最新代。

备份、历史 CSR、恢复任务各自登记依赖，不把“当前 latest 未引用”当作垃圾的充分条件。GC 两阶段标记和延迟删除，有幂等重试；保留目录锁及其兼容行为，实际共享文件系统的锁、原子替换、刷盘和挂载失效行为单独验收。

## 8 回归与发布门禁

优先扩展已有 `tests/engine/sources.rs`、`tests/engine/direct_sources.rs`、`tests/admin/local_tables.rs`、`tests/engine/projected.rs`、`tests/admin.rs` 与 `tests/admin/mcp.rs`。新测试保护可观察行为与故障边界，不添加只验证某字段已删除的断言，也不另建庞大测试框架。

| 层次 | 触发与内容 | 完成判据 |
| --- | --- | --- |
| 每个 PR 和 main | 格式检查；`cargo test --locked --lib --bins --test engine --test admin --features admin`；前端现有测试和构建 | 实际执行图语义、本地表、权限/MCP、预算与取消测试；报告通过、失败和忽略数 |

具体 Rust feature 与 workspace bindings 测试分别列清；Python/C bindings 使用仓库既有 smoke 验证，不能因为 workspace 默认只包含根包就宣称覆盖所有绑定。测试命令实施时以实际目标清单校验。

本地 Linux 后端与服务夹具使用 OrbStack；GitHub Actions 使用原有 Linux runner/container。涉及页面修改时使用本机 Chrome 验证真实后端下的查询诊断、新鲜度、同步策略和恢复流程，检查错误/超时/权限状态及窄屏交互；复用现有工具，不新增 Playwright 等框架。

新增 PR 工作流和发布可复用门禁，发布构建依赖验证成功。同一提交 SHA、锁文件、夹具版本和报告关联到 BUILD-INFO/发布记录。手动触发仍可保留，但不能绕过验证。仓库分支保护/required checks 是独立仓库设置，需要实际配置并读取确认，不能只凭 YAML 声称已强制执行。

## 9 验收矩阵

下表为实施验收目标，不是已测结果。所有性能对照使用同一数据、查询、索引、预算、并发、快照和持久化条件；冷/热缓存分开，至少预热后重复 5 次并保留样本。精确结果使用排序后的类型化值/摘要比对，算法采用其适当不变量和数值容差。

| 场景 | 正确性与恢复 | 成本目标 |
| --- | --- | --- |
| 10 万行 SQLite 三条原查询 | 保存原 DDL 与分布，另建有/无约束两组；结果满足原语义；重复键/动态坏类型仍按契约处理 | 可证明安全路径下三条查询各接收 1 行，LIMIT 0 不读数据；无索引普通属性可在库内扫描 N 行，必须如实报告 |
| SQL/Cypher/Gremlin 简单标签及复杂反例 | 普通属性、NULL、字符串大小写/空格、复合键、同表复用、残余谓词、租户过滤、Join/UNION/SCD2 | 支持路径读量降低；不安全路径明确回退，不能靠少读返回错误结果 |
| MySQL 与 PostgreSQL 时间戳同步 | 10 万/100 万行，更新 100 行，覆盖相同微秒、时区、跨页边界、长事务和重试 | 接收行数为窗口/边界范围内候选数，不是 N；有索引时验证源端计划与 examined rows，无索引标明源端扫描 |
| UUID 与复合键小批更新 | 100 万/1000 万行；新增、替换、删除、重复与空键、租户相同 user_id、编码边界 | 健康索引下不读完整旧表键列，不改写全部基础文件；100 行变更不含整理时总写字节目标低于旧全重写的 10% |
| 100 轮更新与整理 | 包含热点与随机键，跨文件/覆盖位置阈值，查询与同步并发 | 累计数据+索引+整理写字节目标低于逐轮全重写的 20%；记录最坏轮延迟、索引大小和读取放大，未达目标继续定位 |
| 原子发布故障 | 数据刷盘前后、索引提交后、manifest 发布前后、历史落盘前分别杀进程；磁盘满与网络失败 | 恢复后完整 G 或 G+1，水位不超前、没有混代、遗漏或重复；重试幂等，索引失配可重建 |
| 删除与迟到 | 软删除可见、窗口内迟到补齐、窗口外及物理删除由全量对账纠正；对账失败不报成功 | 暴露实测可见延迟、最近成功对账和超限状态；严格查询在条件不满足时拒绝 |
| CSR 新鲜度 | 本地表更新、刷新失败、刷新期间再次更新、源删除授权边、历史代次重放 | 原查询稳定，新查询策略正确，Agent 可见相同新鲜度事实；自动刷新无无限队列 |
| 社区检测与 Node2Vec | 10 万顶点/100 万边，固定种子、权重、孤点及取消；高预算成功并核对结果 | 256 MiB 不足时清晰拒绝；记录成功所需预算及 RSS，优化后实测峰值下降，无取消退化 |
| 1/2/3 Worker | 固定快照结果等价，倾斜/故障重试不丢数据，重试不切换代次 | 小负载 auto 路径 P95 相对本机基线目标不恶化超过 10%；大负载记录加速比和总成本，未实测独立主机不宣称横向收益 |
| 备份与跨站恢复 | 不同根目录/新命名空间、源离线、损坏/缺失文件、暂停调度、后续增量与 CSR | 记录实际 RPO/RTO、数据量与恢复耗时；副本定义、历史、数据及权限全部可用 |
| 托管对象存储 | Worker 无共享挂载；写者失联/旧主复活；查询与 GC 并发；缓存清空 | 一代只发布一次，Worker 读相同固定代次，GC 不删活跃/备份引用，无共享路径前提 |

时间阈值是待基线校准的回归预算，行数、代次一致性和不丢数据是硬判据。报告包含逻辑字节与真实写入量；reflink、缓存、元数据探针及源端扫描不能混为同一种指标。无排序查询按语义比对，不用偶然顺序制造性能失败或掩盖真实错误。

## 10 分阶段实施与文件边界

阶段按依赖顺序交付，每个阶段独立可审查；表中拆分是代码责任范围，不要求并行代理或一次完成大重构。

| 阶段 | 主要改动范围 | 退出条件与依赖 |
| --- | --- | --- |
| S0 基线与门禁 | `.github/workflows/`、现有 tests、`src/source/mod.rs`、查询/同步统计 | 三条查询、时间戳同步、复合键全写与算法预算可重复复现；PR 核心回归实际运行，报告口径统一 |
| S1 类型化下推 | `engine/read_filters.rs`、`sql_read.rs`、`model.rs`、`sources.rs`；SQLite/MySQL/PostgreSQL 驱动 | 唯一性/校验证明和精确性规则完成；原查询与时间戳读取量达标，复杂查询无语义回归；依赖 S0 |
| S2 按需扫描 | SQLite/MySQL/ClickHouse、`source/snapshot.rs`、查询生命周期 | 单消费者首批无需完整物化；取消/重扫/连接恢复有验证；复杂多消费者保留正确 fallback；依赖 S1 |
| S3 通用键增量 | `local_tables/load.rs`、overlay/maintenance、快照清单，新增有明确职责的键索引模块 | 新旧格式可读、UUID/复合键小批与长期成本达标、提交故障恢复通过；依赖 S0/S1 |
| S4 可信数据状态 | local_tables store/scheduler、CSR/cache、query/MCP、`LocalTables.tsx`、`Query.tsx`、`ModelHealth.tsx` | 重读窗口/软删除/对账、严格策略、CSR 自动刷新和 Chrome 真实流程通过；显式水位依赖 S3 |
| S5 算法与调度 | projected graph/community/embedding、cluster config/distributed、API/文档 | 能力与内存预检先交付；随后测量并减少实测内存及小查询分布式开销；依赖 S0，独立主机性能报告另列验收 |
| S6 备份与集群副本 | backup/recovery、local_tables store、cluster control/store、source resolution、恢复 UI | 先完整目录快照恢复，再托管对象存储及 fencing/GC；依赖 S3 的清单和代次；真实故障与 Chrome 恢复验收通过 |
| S7 发布收口 | release workflow、package、部署/监控/技术参考/变更记录 | 同一 SHA 的全部必需门禁和产物 smoke 完成，升级/回退演练通过，发布能力与实测证据匹配 |

第一批实现范围固定为 S0 与 S1：先交付用户最直接感知的读放大修复和时间戳读取改进。S4 的状态展示、S5 的能力说明和 S6 的备份清单设计可以早做，但不得把未实施的新能力写成现有行为。

新清单/来源格式启用前，先发布能够读取旧新两版的程序；集群所有 Worker 完成升级后才允许新写入。需要回退旧程序时，停同步并导出兼容单文件快照/恢复升级前备份，或继续使用兼容读取版本；不能直接让旧程序读取新 manifest。配置/API 新字段默认保持原行为，读旧状态缺失的新鲜度数据记为 unknown。

## 11 文档和交付定义

每阶段同步更新受影响的 [README](../README.md)、[本地表指南](local-tables.zh-CN.md)、[技术参考](reference.zh-CN.md)、[部署指南](deployment.md)、[集群说明](../deploy/cluster.md)、[监控说明](../deploy/monitoring.md)、[MCP 文档](mcp.md) 及发布时的 CHANGELOG。文档明确支持条件、真实运行验证与未验证来源，不把能力矩阵里的计划状态合并为“支持”。

完整交付必须同时具备：可审查的代码与契约、真实复现及优化对照、故障恢复证据、Chrome 受影响流程验证、发布门禁的实际运行记录、迁移与回退说明。新增连接器、任意跨源事务、完整 CDC、自研 Worker 副本以及分布式 Leiden/Node2Vec 均不混入当前阶段；如业务确实需要，按独立设计和验收推进。

各阶段验收以对应实现和验证记录为准。上文未测的量化目标继续用于后续阶段验收。

S7 的发布门禁、滚动升级与回退步骤、OrbStack 运行与复跑命令见 [S7 发布验收](production-optimization-s7.zh-CN.md)。

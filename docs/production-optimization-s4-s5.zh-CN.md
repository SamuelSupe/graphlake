# GraphLake S4 和 S5 实施与验证记录

环境为 OrbStack ARM64 Linux。算法对照使用同一 worktree 的已有 S1 二进制与本次构建。Worker 对照固定一次生成的 SQLite 和四份 Parquet 数据、查询、分区数和输出顺序。以下数据来自同一台宿主机。

## 撤权、对账与严格查询

测试来源包含两条授权。撤权记录的标记推进到水位 131，低于原水位但在窗口内的授权值为 125，窗口外记录为 90，同时物理删除另一条授权。增量完成后，实时查询已看不到撤权边，并找到窗口内记录。原物理删除边仍存在于副本。定时对账完整读取来源后，物理删除边消失，窗口外记录可见。

在撤权前保存了能够查到授权路径的 CSR。撤权时将构建依赖的 SQLite 节点来源暂时移走。增量任务从开始到提交耗时 25 ms。以移动节点来源和写入撤权记录前为计时起点，在 2.133 秒时已观察到 CSR 刷新失败并验证查询结果。发布指针仍是原代次，普通查询得到旧路径，要求当前 CSR 的查询返回 `409 freshness_required`。另一个请求以 1 秒为最大对账年龄，同样被拒绝。30 秒定时对账让物理删除和窗口外记录在 31.065 秒后可见。恢复节点来源之后，退避结束触发新构建，32.152 秒后严格查询在新 CSR 上返回空路径。Chrome 验证了本地表创建、软删除与重读窗口控件、定时对账时间以及严格查询拒绝提示。MCP 回归验证了年龄策略无法满足时返回 `freshness_required`。

观察时间、对账时间与实际 CSR 依赖代次分别返回。定位到历史数据时，查询结果附带相应快照范围。自动刷新在配置后的集群 Coordinator 上工作，构建使用固定输入和原子发布。完整对账的间隔控制健康运行时的轮询目标，源端停机和构建失败会延长实际可见时间。

## 算法预算与取消

固定 100,000 个顶点、1,000,000 条内部 links，Leiden 做两轮迭代，种子 42。两边各三次在 512 MiB 下均完成，按逻辑行排序后全量结果一致，每次得到 2,353 个社区。新版本在投影结束后释放端点查找表，在交给社区求解器前释放已转换的边，并在现有边数组内合并平行边。

| 512 MiB 下的 Leiden | S1 | S5 |
| --- | ---: | ---: |
| 峰值 RSS 中位数 | 277.6 MiB | 255.8 MiB |
| 引擎预留峰值 | 416,595,520 B | 409,295,520 B |
| 端到端耗时中位数 | 5.32 s | 5.25 s |

256 MiB 下的 Leiden 返回 310,400,000 B 的工作区需求以及实际 V/E。`dimensions=512` 的 Node2Vec 在 512 MiB 下返回 411,200,160 B 工作区需求，另计已投影的拓扑内存。CLI 向运行中的 Leiden 发送 `SIGINT`，从发出信号到进程退出约 16 ms。内存预算在本机路径按已投影的实际行数核算。

## 1 / 2 / 3 Worker 对照

SQL 夹具为 50,000 行账户与 100,000 行事件，包含选择性 Join、宽字段 Join/分组和聚合。CSR 夹具为两个分量、128 个节点与 128 条边。每项预热一次，测量五次，所有拓扑结果一致。分区固定为 3。固定总资源模式把 6 个逻辑 CPU 和 384 MiB 单次预算分给各 Worker。固定每 Worker 模式用 2 个 CPU 和 256 MiB。Coordinator 和元数据服务保持同一机器上的独立进程。

| 工作负载 | 每 Worker 固定 P50 / P95，1 → 2 → 3 | 总资源固定 P50 / P95，1 → 2 → 3 |
| --- | --- | --- |
| 选择性 Join | 691/698 → 690/693 → 539/543 ms | 688/692 → 692/696 → 542/547 ms |
| 宽 Join/分组 | 1,306/1,314 → 1,304/1,307 → 999/1,005 ms | 1,303/1,310 → 1,308/1,342 → 999/1,003 ms |
| 局部聚合 | 533/541 → 540/542 → 385/394 ms | 539/549 → 537/541 → 387/394 ms |
| PageRank | 37/43 → 36/41 → 36/39 ms | 37/49 → 63/67 → 37/39 ms |
| 弱连通分量 | 147/151 → 538/539 → 386/551 ms | 174/176 → 535/542 → 381/677 ms |

固定每 Worker 的宽 Join 对照中，Coordinator 与 Worker 总 CPU 中位数为 1.19、1.22、1.20 秒，进程各自的 RSS 高水位之和为约 363、527、658 MiB，Shuffle 各约 5.60 MB。RSS 高水位求和用于估算资源占用，各进程的峰值可能发生在不同时间。两个多 Worker 方案都实际执行了远端分区。

另行提交两条并发宽 Join，两条结果均与单查询一致。固定每 Worker 的一次样本中，1、2、3 Worker 的吞吐分别为 1.37、1.53、1.74 查询/秒。固定总资源时分别为 1.37、1.52、1.74 查询/秒。

同一 3 Worker 夹具启用 `distributed_min_rows: 1024` 后，弱连通分量改为本机处理，远端分区调用从 204 次降至 0，P50 从 386.31 ms 降到 118.50 ms，宽 Join 继续使用远端分区。这个门槛来自此小图对照，部署值应按实际数据选择。

在 1、2、3 Worker 拓扑均杀死正在接单的 Worker。约 6.08、6.08、6.06 秒收到 `worker_lost`，重启后重跑得到原结果。重启 Coordinator 后，通过原请求标识取回重跑的完成结果。核心回归门禁通过 99 项 Rust 测试，真实服务门禁通过 11 项，前端构建及 34 项测试通过。

## 复跑

```bash
docker compose -f tests/production-compose.yml up -d --wait
bash tests/production-services.sh
python3 tests/cluster_scaling_benchmark.py /path/to/graphlake
python3 tests/cluster_scaling_benchmark.py /path/to/graphlake --workers 3 --min-rows 1024 --skip-faults
python3 tests/cluster_scaling_benchmark.py /path/to/graphlake --repeats 1 --skip-faults
```

基准同目录使用对应的 `graphlake-admin`，以本机 etcd 储存任务元数据。可传 `--etcd` 指定隔离实例。性能数据是 OrbStack 上的同宿主对照。独立主机扩容、网络传输与外部对象存储的独立计量，以及专门的倾斜 Join 扩容对照仍需验证。

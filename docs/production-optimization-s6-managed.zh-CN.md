# GraphLake S6 托管本地表与快照回收

托管模式使用集群的 etcd 和 S3 兼容存储。模型以 `local-table://<UUID>` 指向表，查询派发记录固定代次、清单摘要和 etcd 租约。Worker 根据派发记录读 S3。Coordinator 将候选清单和新增数据写入唯一前缀，再用同一个事务校验领导租约和原表记录版本、发布代次及同步结果。普通文件模式继续支持原路径。[配置与迁移](../deploy/cluster.md#s3-托管本地表)

## OrbStack 验证

演练使用真实 PostgreSQL 16、etcd 和 RustFS。源和备 Coordinator 使用不同目录。Worker 在独立 Linux 挂载命名空间运行，启动前把两台 Coordinator 的目录盖成空的 tmpfs，并断言目录不可见。验证脚本阻塞指定的 S3 数据 GET 和 etcd 事务，查询仍通过公开 API 提交。

| 注入点 | 观测 |
| --- | --- |
| 查询和备份同时读取同一代次 | 保留与回收各设为 1 秒。另一个无租约的中间代清单和数据被删除时，两项读取仍在等待。放行后，查询得到水位 10 的三行，备份离线校验通过且记录同一代次。释放已结束查询的测试租约后，原代清单和数据可回收。 |
| 旧主上传完成但还未发布 | 将原 etcd 事务暂留在测试代理中。确认表记录修订仍匹配，撤销旧主租约后把原事务送到 etcd。事务返回失败，表记录和可见数据未变化。新主恢复到已提交水位 12，把未完成任务标为中断，再增量推进到 13。废弃候选文件回收，仍被当前代引用的文件保留。 |
| 接单 Worker 在读取对象时退出 | 重启 Worker，并在重试前将生效水位推进到 14。原请求重试返回其固定水位 13 的数据。随后新请求读到 14。 |
| 原代已回收后恢复托管备份 | 用独立命名空间和 S3 前缀恢复备份。原同步数据库不可达时，隔离 Worker 仍返回备份时的三行。表 ID 和代次保持一致，定时任务保持暂停。 |
| 新主刷新 CSR | 使用新发布的托管代次构建 CSR。要求当前 CSR 的查询成功返回三条弱连通分量结果。 |

从备主启动到增量重试、孤儿回收和 CSR 校验完成，该次小夹具观测为 2.06 秒。99 项核心 Rust 测试、11 项真实服务测试，以及文件和 S3 两组灾备演练均通过。演练使用同一台 OrbStack 宿主机上的隔离进程和数据服务。GC 实测用短周期触发，部署默认保留 24 小时、再延迟 5 分钟回收。普通查询租约保留请求期限和重试缓冲，演练显式撤销了已结束查询的租约，以便观察同一次运行中的物理删除。Coordinator 冷启动后的第一次同步可能要从 S3 下载原代并重建键索引。S3 对象版本和未完成分段上传的生命周期由部署侧管理。

## 复跑

```bash
docker compose -f tests/production-compose.yml up -d --wait
bash tests/production-services.sh
```

回归门禁的 S3 托管演练使用同样的故障注入。要追加实际挂载隔离，可用有 sudo 挂载权限的测试主机执行 `python3 tests/managed_local_tables.py <graphlake-admin 路径> --isolate-worker` 并沿用门禁脚本的夹具环境变量。

# GraphLake S6 本地表备份与跨站恢复

HA 手动备份和定时／CLI 导出会固定本地表的目录状态和已提交代次。控制 JSON 包含定义、来源配置引用、刷新策略、历史以及文件摘要。旁边的 `local-<id>` 目录保存独立 Parquet 或已提交 GLPQ1／GLPQ2 清单和它引用的数据文件。备份复制期间保护文件引用。正在运行的同步在备份历史里标为中断，已完成提交的 GLPQ2 代次仍可从清单核实。派生键索引按需重建。

UI 和 CLI 恢复先校验模型引用、定义、摘要、清单、schema 和行数，再原子安装目标副本目录。业务入口在验收通过前保持关闭。中断重试绑定原检查点，并复用已校验、内容一致的文件。定时刷新和对账在恢复后暂停，原间隔保存在定义里。保存刷新配置即可重新启用。已发布模型使用相对副本路径时，可更换目录而保留模型版本。[备份和恢复操作](../deploy/cluster.md#在线控制状态备份与恢复)

## OrbStack 对照

演练的两站使用独立根目录、etcd、S3 兼容存储和 PostgreSQL 实例。模型包含一张本地账户表及从同批数据派生的授权边，源端先全量再小批更新。测试在 PostgreSQL 上持有表锁，确保下一次增量在读取时等待。

- 手动在线备份在增量仍为 `running` 时完成，耗时约 67 ms。副本包含一份清单、两个数据文件，共 3,433 字节。备份记录原代次和水位 11，受阻的加载在归档中标为中断。定时配置所用的 CLI 导出和两份副本的离线校验也通过。
- 目标拒绝了缺失和篡改的文件，目标副本目录当时尚未安装。在本地目录安装后、PostgreSQL 阶段执行中，停止 Coordinator。重启显示中断并约束为同一备份。重试约 0.75 秒完成到验收开放，包含一次已安装文件被移走时的验收拒绝和修复后重验。
- 目标站的外部同步连接指向不可达地址。验收和查询仍按原模型版本返回 `[1,2,11]`、`[2,2,10]`、`[3,3,10]`，与备份前逐行一致。定时刷新 1,800 秒和对账 3,600 秒仍在配置里，处于暂停状态。Chrome 验证了恢复后状态、保留的间隔和保存配置恢复定时。
- 恢复源连接后，手动增量从备份水位继续，实际接收 4 行，包含窗口内的记录。软删除和新账户生效，结果为 `[2,2,10]`、`[3,3,10]`、`[4,3,13]`，与原站同批数据更新后的结果一致。CSR 自动发布新代，要求当前 CSR 的弱连通分量查询返回 3 个顶点。

CLI 还验证了仅含本地副本的检查点。首次恢复缺失一个数据文件时，目标命名空间保留原检查点并拒绝普通启动。补回文件后，重试与验收通过，源端离线时的查询结果仍逐行一致。

两站的服务和存储实例独立，运行于同一 OrbStack 宿主机。耗时是小数据夹具的演练观测。恢复页面的完整导入使用真实 HTTP 接口验证，Chrome 的恢复页端到端未通过本地证书校验。本文记录便携备份与恢复阶段。集群的 S3 托管发布、etcd 原子代次切换和回收演练见[托管本地表验证记录](production-optimization-s6-managed.zh-CN.md)。

## 复跑

```sh
docker compose -f tests/production-compose.yml up -d --wait
bash tests/production-services.sh
```

验证复用测试 PostgreSQL 16，请使用同主版本的 `pg_dump` 和 `pg_restore`。单独运行可调用 `python3 tests/local_backup_recovery.py <graphlake-admin 路径>`，并设置生产回归脚本中的连接环境变量。可用 `GRAPHLAKE_RECOVERY_TEST_ETCD`、`GRAPHLAKE_RECOVERY_TEST_AWS_ENDPOINT` 和 `GRAPHLAKE_RECOVERY_TEST_POSTGRES` 指向另一套隔离的夹具。
